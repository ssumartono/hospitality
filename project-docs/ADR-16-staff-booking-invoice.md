# ADR-16 — Booking petugas, kesiapan awal dan invoice

2 November2026. Irisan B03.3/B04.3/B07.1/B07.2/B08.1/B18.

Booking dicatat Owner/Manager berizin lokasi dengan customer minimum nama/kontak, quote aktor yang valid, plannedMonths1–60 dan konfirmasi policyAccepted/consentNote yang eksplisit. Consent provenance staff_recorded, bukan acceptance akun penghuni/tanda tangan perjanjian. Customer tenant-scoped dan akses melalui customer_locations; tidak mengundang calon penghuni menjadi staf. Data asli tidak di-seed. Intake pending tidak memblokir kamar.

Request menyimpan snapshot quote, expiry, identitas pelanggan terpisah dan consent event append-only. Sebelum accept wajib snapshot masih segar (expiry/kamar/policy), versi pending sesuai, entitlement aktif, room ready/capacity/presence/interval bebas. Bila quote berubah/kedaluwarsa: refresh quote pending dengan konfirmasi baru, bukan ganti harga diam-diam. Periode quote awal berbeda dari requestedEnd(null ongoing). plannedMonths adalah rencana, tidak mengakhiri presence/alokasi ongoing diam-diam.

Accept atomik: entitlement→location→pricing→room→booking lock, snapshot final, invoice dan line initial immutable, nomor unik organisasi, allocation hold/stay, state, audit dan business outbox. Minimum booking>0 menghasilkan held/deadline DB; minimum0 confirmed tanpa payment/receipt, invoice tetap unpaid bila total>0. Due invoice awal held mengikuti hold deadline lokal; minimum0 mengikuti tanggal masuk. dueDay kebijakan dipakai routine billing mendatang. Tidak ada cash ledger atau upload proof/verify pada fase ini.

Kesiapan AWAL adalah command tersendiri dengan version/reason, checklist nyata lengkap/recorded, tidak ada presence/histori occupancy atau workorder blocking, dan tidak ada operational block pada tanggal lokasi saat ini. Reservation/future block tetap dicek pada accept/availability; ready bukan available. Tabel work_orders merupakan fondasi blocker tanpa command penyelesaian layanan dulu. Kamar bekas occupancy wajib turnover workflow mendatang, tidak lewat initial-ready. Tidak melemahkan readiness hanya demi fixture.

Worker role terpisah memproses satu expiry held per transaksi via fungsi terbatas: lock lokasi/room/booking, cek state/deadline lagi, release allocation, void initial invoice belum bertransaksi, audit/outbox. Tidak ada proof/payment workflow aktif; sebelum mengaktifkannya wajib memperluas guard expiry/review/ledger race. Confirmed minimum0 tidak boleh expired. Outbox internal diproses menjadi notifikasi in-app per anggota Owner/Manager/Finance berizin, unique event+recipient. Email bisnis pelanggan belum diaktifkan, tidak mengklaim delivered. SMTP identity/staf tetap adapter lokal/at-least-once.

Invoice issued/void immutable, line append hanya tx penerbitan, adjustment foundation append-only. Read balance saat ini issued original total/void0, verified allocation0 karena payment belum tersedia; adjustment baru schema tanpa command. Sebelum mengaktifkan payment/adjustment wajib mengintegrasikan read model ledger dan void/expiry guards. Tidak ada paid flag input. Void expiry bukan delete; counter rollback bersama transaksi. Source booking accepted dikuatkan deferred constraint invoice+allocation; hanya origin staff yang dikelola command baru, fixture fondasi lama originNULL tetap structural TEST_ONLY dan tidak diberi runtime insert.
